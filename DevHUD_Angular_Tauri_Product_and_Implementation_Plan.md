# DevHUD — Angular + Tauri Product & Implementation Plan

> **Project name:** DevHUD  
> **Tagline:** Your development context, always within reach.  
> **Product vision:** A local-first developer productivity HUD that keeps sprint context, quick notes, blockers, reminders, work history, and secure credentials close at hand without interrupting coding.  
> **Desktop framework:** Tauri v2  
> **Frontend:** Angular + TypeScript (Angular CLI)  
> **Backend:** Rust  
> **Database:** SQLite

---

## 1. Important Technology and Project-Structure Decision

**DevHUD will use Angular + TypeScript with Tauri v2. It will not use React, Vite, or a custom frontend scaffold.**

The project must be created with the official Tauri scaffolder and the Angular template:

```bash
npm create tauri-app@latest
```

In the interactive prompts, select:

1. **Project name:** `devhud`
2. **Identifier:** a unique application identifier, for example `com.yourcompany.devhud`
3. **Frontend language:** TypeScript / JavaScript
4. **Package manager:** npm
5. **UI template:** Angular
6. **UI flavor:** TypeScript, if the prompt is shown

The current `create-tauri-app` template list includes `angular`. Angular uses the Angular CLI project structure; do not create a separate React/Vite frontend or move the generated files into a new custom folder. The Tauri Rust project remains inside `src-tauri/`. See the official [Tauri Create a Project guide](https://tauri.app/start/create-project/) and [Tauri Project Structure guide](https://tauri.app/start/project-structure/).

### 1.1 What the generated project structure means

- **Project root:** Angular CLI configuration and npm scripts, such as `package.json`, `angular.json`, and TypeScript configuration.
- **`src/`:** Angular application source. Keep Angular's `main.ts`, `index.html`, and `app/` structure.
- **`src-tauri/`:** Tauri configuration, Rust crate, capabilities, icons, and native desktop code.
- **`src-tauri/src/`:** Rust entry points and the application modules we add as DevHUD grows.

The scaffold's exact minor-version files can evolve. Treat the files generated by the installed `create-tauri-app` version as the source of truth. Add DevHUD feature folders inside the generated structure; do not replace or reorganize the Tauri scaffold unnecessarily.

### 1.2 Commands after scaffolding

Use the package manager and scripts printed by the generator. A typical workflow is:

```bash
cd devhud
npm install
npm run tauri dev
```

Before changing build configuration, inspect the generated `package.json`, `angular.json`, and `src-tauri/tauri.conf.json`. Keep the Angular development-server command, Tauri `devUrl`, Angular build output, and Tauri `frontendDist` aligned with the values generated for the project. Do not copy a Vite configuration into this Angular project.

## 2. Product Vision

DevHUD is a lightweight desktop companion that keeps important development context visible without forcing developers to leave their IDE.

It brings together:

- Current sprint goals, tasks, blockers, and production notes.
- A fast-capture inbox for ideas and work discovered while coding.
- Reminders and alarms that are noticeable but not disruptive.
- Searchable sprint history and stand-up / retrospective summaries.
- A local encrypted credential vault for development accounts and environments.
- A compact, keyboard-first overlay that can stay above the IDE.

**Core promise:** Capture quickly, remember reliably, retrieve instantly, and stay in the development flow.

DevHUD is not intended to replace Jira, Azure DevOps, GitHub, Notion, or a team's project-management system. It is a personal context layer that helps a developer manage the information needed while working.

## 3. Product Principles

1. **Non-intrusive by default:** No unexpected focus stealing, modal interruptions, or noisy animations.
2. **Fast capture:** A task, note, blocker, or idea should take only a few seconds to record.
3. **Local-first:** Core functionality works offline. No account or network connection is required.
4. **Safe by design:** Credentials are encrypted, Tauri capabilities are narrowly scoped, and backups are protected.
5. **Recoverable:** Data should survive application crashes, upgrades, and accidental deletion.
6. **Keyboard-friendly:** Common actions are available through shortcuts and a command palette.
7. **Sprint-aware, not sprint-limited:** Information can belong to a sprint, a personal inbox, or a reusable reference collection.
8. **Progressively enhanced:** Ship a dependable core before adding integrations and advanced automation.
9. **Angular-native:** Use Angular standalone components, services, dependency injection, routing, signals, and Angular CLI conventions.
10. **Tauri-native:** Keep native desktop behavior and sensitive operations in Rust, and use Tauri commands / events as the explicit frontend-backend boundary.

## 4. Target Users and Main Workflows

### Primary user

A developer working across multiple tasks, environments, repositories, and releases who needs quick access to personal work context.

### Key workflows

**Start the workday**
1. Open DevHUD automatically or with a global shortcut.
2. See the active sprint goal, in-progress tasks, blockers, and today's reminders.
3. Select the task currently being worked on.

**Capture something while coding**
1. Press the quick-capture shortcut.
2. Enter a short sentence.
3. Choose or accept the suggested type: task, note, production reminder, blocker, or future idea.
4. Save without switching away from the IDE.

**Prepare for a production release**
1. Open the production checklist.
2. Review critical environment-specific notes.
3. Mark each item as verified.
4. Keep unresolved items visible until they are addressed.

**Prepare for stand-up**
1. Open the current sprint summary.
2. Review completed, in-progress, and blocked work.
3. Copy a concise summary.
4. Edit it before sharing with the team.

**Retrieve a credential**
1. Open the vault using its shortcut.
2. Unlock if necessary.
3. Search by title, URL, username, or tag.
4. Copy the requested field through a backend-controlled clipboard operation.
5. Let the clipboard clear safely after the configured interval, when supported.

## 5. Feature Specification

### 5.1 Always-on-top HUD

The HUD is the defining feature. It should be useful in compact and expanded states.

**Window behavior**
- Frameless, transparent, always-on-top window.
- Draggable and resizable, with saved size and position.
- Remember position per display where supported.
- Start minimized, compact, or expanded according to user preference.
- Optional launch at operating-system startup.
- Hide/show through a global shortcut.
- Close-to-tray behavior with an explicit quit action.
- Restore safely after display resolution or monitor changes.
- Configurable opacity and compact / expanded layouts.
- Keep the HUD above the IDE without taking keyboard focus during passive refreshes.

**Interaction modes**
- **Interactive mode:** Normal mouse and keyboard interaction.
- **Click-through mode:** Mouse events pass through the HUD to the application underneath.
- **Temporary interaction mode:** A shortcut temporarily restores HUD interaction.
- **Focus mode:** Shows only the selected task, active blockers, and due alarms.
- **Compact mode:** Shows a small status bar with sprint name, current-task indicator, and urgent reminder count.

Click-through, transparency, focus behavior, and window stacking differ between Windows, macOS, and Linux window managers. Treat these as a Phase 0 technical spike. Do not promise identical behavior across platforms until it has been tested on each target OS.

**HUD cards**
- Current sprint and goal.
- Current task.
- Today's tasks and due items.
- Active blockers.
- Production reminders.
- Upcoming alarms.
- Quick capture.
- Vault shortcut (never display secrets directly on the HUD).

**Important UX rules**
- Do not steal IDE focus when refreshing data or receiving an alarm.
- Do not show sensitive vault values in HUD previews.
- Keep animations limited to meaningful state changes.
- Allow the user to pause, hide, or reposition the HUD immediately.
- Provide a reliable way to temporarily disable click-through; the user must never get trapped in a non-interactive HUD state.

### 5.2 Sprint Workspace

**Sprint management**
- Create, edit, activate, complete, and archive sprints.
- Store sprint name, goal, start date, end date, and status.
- Permit only one active sprint by default.
- Warn before creating overlapping active sprint periods.
- Support a sprint without fixed dates for personal workflows.

**Work item types**
- Task
- Production note
- Future-work idea
- Blocker
- General note

**Task fields**
- Title and description.
- Status: `todo`, `in_progress`, `blocked`, `done`, `cancelled`.
- Priority: `low`, `normal`, `high`, `critical`.
- Optional due date and reminder.
- Tags.
- Created, updated, started, and completed timestamps.
- Optional source / reference URL.

**Production checklist**
- Group items by environment, release, or category.
- Include a verification checkbox and optional verification note.
- Keep critical unresolved items prominent.
- Preserve checked / unchecked state in sprint archives.
- Support reusable checklist templates in a later milestone.

**Quick capture**
- One-line capture from the HUD.
- Global shortcut opens a small capture window or compact capture surface.
- Default destination is the current sprint.
- Allow capture into a global inbox when the correct sprint is unknown.
- Support simple type prefixes:
  - `task: Fix refresh issue`
  - `blocker: Waiting for API access`
  - `prod: Verify production callback URL`
  - `idea: Add offline export`
  - `note: Retry logic is in tracking_service.rs`
- Allow conversion between item types without losing the original creation time.
- Never silently discard text when the user closes the capture surface.

### 5.3 Personal Inbox and Knowledge Notes

Not every useful thought belongs to the active sprint.

- A global inbox for uncategorized captures.
- Review and triage inbox items into a sprint, reference note, or backlog.
- Pinned notes for frequently used development information.
- Tags and optional categories.
- Markdown support for code snippets, links, and formatted notes.
- Full-text search across titles, descriptions, notes, and tags.
- Optional links between a task and a note.
- Archive or delete with a recovery period.

Keep this feature lightweight. DevHUD should not become a full document editor.

### 5.4 Sprint History and Reporting

**Archive**
- Archive a sprint with a consistent snapshot of its tasks, notes, blockers, production checklist, and future-work items.
- Preserve original timestamps and final statuses.
- Do not silently modify an archived snapshot when the current sprint changes.
- Require confirmation before destructive archive operations.

**History browser**
- Search by sprint name, date range, keyword, tag, item type, and status.
- Filter completed, incomplete, cancelled, and carried-over work.
- Open an archived sprint to inspect its snapshot.
- Show a timeline of sprint activity.

**Carry-over**
- Select individual unfinished items to carry into the active sprint.
- Create a new item linked to its original item rather than moving and destroying history.
- Preserve the original sprint reference.
- Avoid duplicate carry-over when an item has already been copied.

**Stand-up and retrospective summaries**
- Generate summaries from actual stored activity.
- Sections: completed, in progress, blocked, carried over, and upcoming.
- Let users edit generated text before copying.
- Support Markdown and plain-text copy.
- Clearly distinguish recorded facts from manually written reflections.

**Sprint comparison**
- Compare planned versus completed work.
- Show counts by status and priority.
- Show carry-over counts and unresolved blockers.
- Avoid claiming formal team velocity from personal task counts unless the user configures estimates and understands the limitations.

### 5.5 Reminders and Alarms

**Reminder types**
- Task due-date reminder.
- Custom one-time alarm.
- Repeating alarm.
- Sprint-end review reminder.
- Production checklist reminder.
- Follow-up reminder for a blocker.

**Behavior**
- Local OS notification plus an in-HUD indicator.
- Snooze: 5 minutes, 15 minutes, 1 hour, or custom.
- Dismiss, complete, or open the related item.
- Repeat rules: daily, weekly, selected weekdays, or custom interval.
- Persist reminder state so app restarts do not lose pending reminders.
- Handle sleep, resume, timezone changes, and missed alarms.
- Prevent duplicate notifications when the app resumes.
- Respect quiet hours and Do Not Disturb settings.
- Provide a test-notification action.

**Important delivery boundary**

The first implementation should guarantee reminders while DevHUD is running, including when it is minimized to the system tray. Do not assume a normal in-app timer or a basic Tauri notification call can deliver scheduled alerts after the application has fully exited. If reminders must fire while DevHUD is completely closed, create a separate platform-feasibility task for native OS scheduling / background execution on Windows, macOS, and Linux. Document the supported behavior per platform.

**Scheduling design**
- Store the intended trigger time and timezone context.
- Calculate the next occurrence in a dedicated Rust scheduling service.
- Treat snoozing as a separate occurrence state; do not overwrite the original recurrence rule.
- Use stable reminder IDs and occurrence IDs to prevent duplicate delivery.
- Reconcile overdue occurrences on application startup and system resume.

### 5.6 Encrypted Credential Vault

The vault is security-sensitive and should be implemented only after the core productivity features and backup / restore are stable.

**Vault features**
- Master-password unlock.
- Search by title, URL, username, and tag.
- Credential types: login, API token, database connection, SSH-related reference, and secure note.
- Copy username, password, or token.
- Open the associated URL.
- Password generator with configurable length and character sets.
- Auto-lock after inactivity.
- Lock on application exit and optionally on OS lock / suspend.
- Clipboard auto-clear after a configurable delay.
- Import / export through an explicitly protected workflow.
- No credential contents in logs, crash reports, analytics, or notification text.

**Cryptographic design**
- Use Argon2id to derive a key from the master password and a unique random salt.
- Select and benchmark Argon2id parameters for the supported devices; store the KDF parameters and format version so they can be upgraded later.
- Use a vetted AES-256-GCM implementation for authenticated encryption.
- Generate a fresh, cryptographically secure nonce for every encryption operation; never reuse a nonce with the same key.
- Store salt, nonce, KDF parameters, ciphertext, and format version as required for decryption.
- Use authenticated additional data to bind encrypted records to their record IDs and field purpose where appropriate.
- Zeroize secret buffers when practical and minimize the time secrets remain in memory.
- Never store the master password.
- Version the vault format so future cryptographic migrations are possible.

**Metadata and search decision**

Treat vault titles, URLs, usernames, tags, and notes as potentially sensitive. The safest initial design is to encrypt the complete vault item payload and perform search inside the Rust backend while the vault is unlocked. Do not place decrypted values in SQLite FTS indexes or ordinary logs. If a later version adds plaintext search metadata for performance, make the metadata exposure explicit and opt-in.

**Key management**
- Do not store the raw master password or derived vault key in SQLite.
- Keep the derived key in backend memory only while unlocked; clear / zeroize it on lock where practical.
- Consider optional OS-keychain-backed convenience unlock only after the master-password flow is secure and clearly explained.
- A keychain convenience mode must not silently weaken the master-password security model.
- Document recovery limitations: if the master password and all recovery material are lost, encrypted data may be unrecoverable.

**Clipboard safety**
- Prefer a Rust-side clipboard operation so the secret does not need to be returned to Angular just to be copied.
- Clear the clipboard only if it still contains the exact secret DevHUD copied. Do not erase newer content copied by another application.
- Warn that clipboard managers and OS-level clipboard history may retain copied secrets.
- Never log clipboard contents.
- Keep the auto-clear interval configurable.
- If the clipboard backend cannot verify that the clipboard still contains DevHUD's copied value, do not blindly clear the clipboard.

**Tauri IPC restrictions**
- Expose purpose-specific commands such as `vault_unlock`, `vault_search`, `vault_copy_field`, and `vault_lock`.
- Never expose a generic decrypt-anything or arbitrary-file-read command.
- Validate record IDs and requested fields in Rust.
- Keep encryption and database access in the Rust backend.
- Return only the minimum data required by the UI.
- Never return password or token values to Angular when a backend-controlled clipboard operation can perform the copy.

### 5.7 Command Palette and Keyboard Navigation

Add after the basic HUD and capture flow work reliably.

- `Ctrl/Cmd + K`: open command palette.
- Search tasks, notes, sprints, and vault metadata (without exposing secret values).
- Quick-add task, note, blocker, or idea.
- Switch HUD mode.
- Open reminders.
- Navigate to current or archived sprint.
- Lock the vault.
- Show keyboard shortcut help.
- Support arrow-key navigation, Enter to select, and Escape to close.
- Make keyboard focus visible and restore focus predictably after closing the palette.

### 5.8 Settings and Personalization

- Theme: dark, light, and system.
- HUD opacity, size, and default mode.
- Per-monitor position where supported.
- Global shortcut customization with conflict detection.
- Startup behavior and tray behavior.
- Reminder sound and notification preferences.
- Quiet hours / Do Not Disturb schedule.
- Default sprint and quick-capture destination.
- Vault auto-lock and clipboard timeout.
- Backup location and backup reminder.
- Data export and restore.
- Privacy and security information.

### 5.9 Backup, Restore, and Data Portability

This should be part of the MVP foundation, not an afterthought.

- Automatic local database backup before schema migrations.
- User-triggered backup.
- Configurable backup retention.
- Restore preview before replacing current data.
- Export non-secret productivity data to JSON or Markdown.
- Export vault data only through a separate encrypted export flow.
- Validate backup integrity before restore.
- Warn when a backup is older than the current database.
- Never create an unencrypted backup containing vault plaintext.
- Document where local application data is stored on each operating system.

### 5.10 Reliability and Privacy

- Work fully offline for core functionality.
- No telemetry by default.
- No network calls for fonts, icons, or essential UI assets.
- Structured logs with secret redaction.
- Database transactions for multi-step changes.
- SQLite foreign keys enabled.
- Database migrations with version tracking.
- Graceful handling of locked databases and disk-full errors.
- Recover from invalid saved window positions.
- Prevent duplicate scheduled jobs and notifications.
- Provide a clear data directory and backup location in settings.

## 6. Recommended Architecture

### 6.1 Architecture responsibilities

**Angular frontend**
- Renders HUD cards, sprint workspace, inbox, history, reminders, vault screens, and settings.
- Handles view state, forms, validation feedback, and user interaction.
- Calls Rust through a typed Tauri bridge service.
- Does not directly open SQLite files or implement cryptography.
- Does not store vault master passwords or decrypted credential collections in browser storage.

**Tauri desktop layer**
- Owns the desktop application lifecycle and webview windows.
- Configures window properties, system tray, global shortcuts, notifications, and capabilities.
- Provides the IPC boundary between Angular and Rust.
- Keeps each window's permissions as narrow as possible.

**Rust backend**
- Implements business rules, persistence, scheduling, encryption, clipboard operations, and native OS integration.
- Exposes purpose-specific Tauri commands and events.
- Validates all command input; never trusts frontend validation alone.

**SQLite**
- Stores local productivity data, reminder state, application settings, and encrypted vault payloads.
- Uses migrations, transactions, foreign keys, indexes, and FTS5 for non-secret search.

**Angular implementation rules**
- Prefer standalone components and lazy-loaded feature routes.
- Use Angular services for API / Tauri communication and reusable business-facing frontend logic.
- Use Angular signals for local and shared UI state where they fit; use RxJS for asynchronous streams and event subscriptions where appropriate.
- Keep components focused on presentation and interaction. Do not place SQL, cryptography, scheduling rules, or complex business logic in components.
- Centralize all `invoke`, Tauri event listeners, and plugin API calls behind typed Angular services.
- Unsubscribe / dispose Tauri event listeners when the owning Angular service or component is destroyed.
- Use reactive forms for structured forms such as sprint/task editing and vault setup.
- Use Angular Router for full dashboard sections. For separate Tauri windows, use explicit window labels and a known Angular route or startup parameter; test routing with the generated Tauri asset protocol before choosing path versus hash routing.
- Use Angular CDK for accessible overlay, focus management, keyboard handling, and drag/drop where useful.
- Use SCSS / CSS variables for the HUD visual system. Tailwind CSS is optional; do not add it just because it appeared in a React-oriented draft.
- Angular Material is optional for standard accessible controls. The custom HUD can use a small set of handcrafted components. React-only libraries such as shadcn/ui are not part of this Angular stack.

### 6.5 Frontend-to-Rust communication

Create one Angular `TauriBridgeService` that wraps Tauri APIs and exposes typed application methods. Feature services call this bridge; components call feature services.

Example layering:

```text
HUD component
   ↓
SprintFacade / WorkItemService (Angular)
   ↓
TauriBridgeService (typed invoke wrapper)
   ↓
Tauri command (Rust command handler)
   ↓
Domain service
   ↓
Repository
   ↓
SQLite
```

Implementation rules:
- Use Tauri v2's frontend API package and the core `invoke` API from the generated Angular application.
- Keep command names and request / response DTOs explicit and typed in TypeScript.
- Validate inputs again in Rust.
- Return structured, user-safe errors; do not leak SQL errors, filesystem paths, or secret details into the UI.
- Use Tauri events for one-way backend notifications such as reminder-due or vault-lock events. Do not use events as a substitute for request/response commands.
- Keep plugin permissions in the Tauri capability files and grant only the permissions each window needs.
- Do not enable broad filesystem, shell, or arbitrary command permissions for convenience.

## 7. Technology Choices

| Layer | Recommended choice | Notes |
|---|---|---|
| Desktop shell | Tauri v2 | Generated by `create-tauri-app`; keep its configuration structure |
| Frontend framework | Angular + TypeScript | Use the Angular template and Angular CLI |
| Frontend architecture | Standalone components, Router, DI, signals, RxJS | Use Angular-native patterns |
| Styling | SCSS / CSS variables; optional Tailwind | Keep the overlay small and visually consistent |
| Accessible UI helpers | Angular CDK; optional Angular Material | Add only what the interface needs |
| Backend | Rust | Native integration, business rules, persistence, security |
| Database | SQLite | Reliable local persistence |
| Rust database access | `rusqlite` (recommended) or SQLx | Choose one approach; do not mix casually |
| Search | SQLite FTS5 | Index non-secret productivity text only |
| Serialization | Serde | Rust models and Tauri command payloads |
| Time | `time` or `chrono` | Choose one primary time library and standardize UTC storage |
| Password KDF | Argon2id | Master-password key derivation |
| Encryption | AES-256-GCM from a vetted Rust crate | Authenticated encryption |
| Secret handling | `zeroize` | Reduce secret lifetime in memory |
| Desktop integration | Tauri v2 APIs and official plugins where suitable | Shortcuts, notifications, clipboard, opener, startup, window behavior |
| Testing | Rust tests + Angular tests + desktop integration tests | Validate all three layers |

**Dependency rule:** Use Tauri v2-compatible plugin versions. Verify plugin maintenance, permission requirements, platform support, and security before adopting them. Do not install every plugin at project creation. Add a plugin when a concrete feature needs it.

## 8. Data Model

Use UUIDs for entity IDs, UTC timestamps for stored instants, and explicit timezone information for user-configured schedules where needed.

| Entity | Important fields |
|---|---|
| `Sprint` | id, name, goal, start_at, end_at, status, created_at, archived_at |
| `WorkItem` | id, sprint_id, type, title, description, status, priority, due_at, completed_at, created_at, updated_at, source_item_id |
| `Note` | id, sprint_id, title, content, pinned, created_at, updated_at |
| `Tag` | id, name, color |
| `WorkItemTag` | work_item_id, tag_id |
| `Reminder` | id, work_item_id, title, trigger_at, timezone, repeat_rule, enabled |
| `ReminderOccurrence` | id, reminder_id, scheduled_at, snoozed_until, delivered_at, dismissed_at, completed_at |
| `SprintArchive` | id, sprint_id, snapshot_json, archived_at, schema_version |
| `ActivityEvent` | id, entity_type, entity_id, action, occurred_at, safe_metadata |
| `VaultItem` | id, encrypted_payload, nonce, format_version, created_at, updated_at |
| `VaultConfig` | id, salt, kdf_parameters, format_version, verifier_cipher |
| `AppSettings` | key, value, updated_at |

### Data-model rules

- Use foreign keys and appropriate indexes.
- Enable SQLite foreign-key enforcement on every connection.
- Use transactions for operations that update multiple related records.
- Use soft deletion or a recovery area for important user-created items.
- Keep archive snapshots independent from live records.
- Store vault ciphertext separately from ordinary productivity content.
- Do not put secrets in `ActivityEvent`, search indexes, logs, or backup metadata.
- Add database migrations from the first version.
- Use an FTS5 index for searchable non-secret content only.
- Define deletion behavior explicitly: cascade, restrict, or preserve an archive reference.
- Decide and document whether vault items are included in application backups; never export them as plaintext.

## 14. Risks and Decisions to Resolve Early

| Risk | Mitigation |
|---|---|
| Click-through differs across operating systems | Build a cross-platform prototype in Phase 0 |
| Transparent windows can affect performance or rendering | Keep the HUD visually simple and profile on real hardware |
| Overlay becomes distracting | Compact mode, focus mode, opacity, and quiet behavior |
| Reminder scheduling becomes unreliable after sleep | Persist occurrences and reconcile on resume |
| Reminders expected while app is fully exited | Treat native OS scheduling as a separate platform-specific requirement |
| Sprint archives become inconsistent | Snapshot records transactionally |
| Vault implementation creates a false sense of security | Threat model, narrow IPC, security tests, and review |
| Clipboard managers retain copied secrets | Explain OS limitations and keep clipboard exposure short |
| Database corruption or accidental deletion | Backups, restore validation, and recovery design |
| Angular components become too large | Feature folders, facade services, reusable components, and lazy routes |
| Tauri permissions become too broad | Keep capabilities scoped per window and feature |
| Too much scope delays delivery | Ship vertical slices and keep the vault separate |

### Decisions to make before implementation

1. Which operating systems are first-class targets for the initial release?
2. Should the HUD be interactive by default, or click-through by default?
3. Should the first version support multiple active sprints, or one active sprint?
4. Should production notes be sprint-specific, reusable templates, or both?
5. What is the minimum supported backup and recovery experience?
6. Should vault convenience unlock through the OS keychain be supported, or should the first vault release require the master password every time?
7. Must reminders fire after DevHUD has been fully exited, or is tray-resident operation acceptable for the first release?
8. Should quick capture use a second Tauri webview window from the beginning, or should it start as a compact surface inside the main HUD?

## 15. Recommended Development Order

The most effective implementation order is:

1. **Create the official scaffold:** Angular + TypeScript + Tauri v2 with `npm create tauri-app@latest`.
2. **Prove the overlay:** Transparent window, always-on-top, focus preservation, click-through, and shortcuts.
3. **Build the data foundation:** SQLite, migrations, repositories, and typed Rust commands.
4. **Deliver the sprint workflow:** Tasks, blockers, production notes, future ideas, and quick capture.
5. **Make reminders dependable:** Persisted scheduling, tray behavior, and OS notifications.
6. **Protect user data:** Backups, restore, and crash recovery.
7. **Add history:** Archives, search, carry-over, and reports.
8. **Build the vault:** Separate threat model and security-focused implementation.
9. **Polish and release:** Cross-platform testing, documentation, and portfolio demo.

**First milestone definition of done:** DevHUD can stay visible above the IDE, be hidden and restored with a shortcut, display the active sprint, manage tasks and blockers, capture notes quickly, and persist everything locally. It must not steal focus during passive updates. The project must retain the generated Angular CLI + Tauri `src-tauri/` structure.
